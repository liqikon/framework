### 핵심 개념: 검수 자동화 체이닝

이번 주차의 핵심은 **기능명세서에서 완료보고서까지의 6단계 자동화 체이닝**이다.

```
기능명세서 (F-001~F-010) + API스펙 (24개 엔드포인트)
    |
    v  [P-501] -- 단, W3 P-309 단계에서 #15 초안이 생성되어 있을 수 있음
테스트 시나리오 (TC-001~TC-060)              -- Step 15/17
    |
    v  [P-502]
Jest 테스트 코드 (6~9개 파일)                -- Step 16/17
    |
    v  [P-503 + GitHub Actions]
테스트 실행 결과 + 배포
    |
    v  [P-505]
배포 후 검증 보고서 (05.리포트/, 파생)
    |
    v  [P-504]
테스트결과보고서.md                          -- Step 16 보강
    |
    v  [P-208]
완료보고서.md                                -- Step 17/17 (Phase 4 Gate Pass)
    |
    +--> [P-506] 온디맨드 리포트 (배포가이드, 결제연동가이드 등 파생 자료)
```

> **Phase 4 Gate-Check 통과 기준**: (a) 구현 산출물 4건 등록 + (b) 백엔드/프론트엔드 코드 동작 + (c) 라이브 배포 URL 1개 이상 + (d) Pass Rate 80% 이상 + (e) 완료보고서 작성. 5개 모두 통과해야 5주 여정의 최종 인증(.progress.md 100%)이 부여된다.

## 3. 강의 슬라이드 요약

### 3.1 과제 리뷰 + Phase 4 Gate-Check 안내 (20분)

**핵심 메시지**: "코드가 만들어졌고 배포되었으니, 이제 검증해야 한다"

전달 포인트:
- 수강생 2-3명의 구현 설계 + 코드 + 배포 결과 공유
- AI 생성 코드 리뷰 결과: 보안 취약점(SQL 인젝션, 인증 우회) 사례
- 프론트-백엔드 통합 및 배포 시 겪은 이슈 공유
- **Phase 4 Gate-Check 5개 항목** 사전 안내: 구현 산출물 + 코드 + 배포 + 테스트 + 완료보고서

> **강사 노트**: W4 과제에서 풀스택 코드 전체를 완성하지 못한 수강생이 있을 수 있음. 구현 설계 4건 + 백엔드 기본 코드 + 1회 이상 배포 완료했다면 W5 실습 참여에 지장 없다고 안내. AP-Rodi-Shop의 코드를 참조하도록 유도. **이번 주차가 끝나면 .progress.md 가 100%로 갱신되어 Phase 4 Gate Pass 인증이 부여됨을 사전 공지**한다.

### 3.2 강의 1: 테스트 전략과 AI 자동화 (30분)

**핵심 메시지**: "AI가 테스트를 생성하고, PM이 무엇을 테스트할지 결정한다"

전달 포인트:

| 주제 | 내용 | 시간 |
|------|------|------|
| 테스트 피라미드 | 단위 -> 통합 -> E2E 구조, 비용/속도 트레이드오프 | 6분 |
| PM이 알아야 할 테스트 전략 | 무엇을 테스트할지 결정하는 것이 PM의 역할 | 5분 |
| AI 기반 테스트 자동화 흐름 | P-501 -> P-502 -> P-503 -> P-504 6단계 체이닝 | 7분 |
| Mock 전략과 한계 | DB 없이 비즈니스 로직만 테스트하는 원리, P-505 보완 필요성 | 6분 |
| CI/CD 개념 | push만 하면 테스트 -> 빌드 -> 배포가 자동으로 진행 | 6분 |

테스트 피라미드:

```
         /  E2E  \         -- 소수, 느림, 비용 높음 (Playwright)
        / 통합 테스트 \      -- 중간 (Supertest)
       / 단위 테스트    \    -- 다수, 빠름, 비용 낮음 (Jest)
       --------------------
       / 배포 후 수동 검증 \  -- 환경 의존 이슈 (P-505)
```

AI가 테스트에 기여하는 영역:

| AI가 생성하는 것 (80%) | PM이 판단하는 것 (20%) |
|----------------------|----------------------|
| 테스트 시나리오(정상/비정상/경계값) | 테스트 전략, 우선순위 결정 |
| Jest 테스트 코드 | 합격 기준(Pass Rate) 설정 |
| CI/CD 워크플로우 파일 | 배포 승인, 릴리스 판단 |
| 커버리지 리포트 분석 | 품질 기준, 결함 허용 수준 |
| 배포 후 검증 체크리스트 결과 정리 | 릴리스 Go/No-Go 판단 |

Mock 전략 (DB 없이 테스트하기):

| 계층 | 실제 사용 | Mock 처리 |
|------|---------|-----------|
| HTTP (Supertest) | 실제 Express 앱 | - |
| Controller | 실제 컨트롤러 | - |
| Model | - | jest.mock() |
| Database | - | jest.mock(config/db) |

> **강사 노트**: 비개발자 수강생에게 Mock은 "가짜 DB 대역 배우"로 비유. "실제 DB가 없어도 비즈니스 로직이 올바른지 확인하는 방법"으로 설명. **Mock의 한계(환경 의존 이슈 미발견)는 P-505 배포 후 검증으로 보완함**을 강조. Document Chaining Step 15-17이 이번 주차에서 완성되며, **온디맨드 리포트(P-506)는 17단계 외 자유 형식 파생 자료**임을 구분 설명.

**Step 2: P-501 테스트 시나리오 생성/정밀화 (20분)**

```bash
- TC-ID 체계: TC-001부터 순번

- 합격 기준 명시 (Pass Rate 80% 이상)

기존 04.검수문서/테스트시나리오.md 초안이 있으면 보강하고, 없으면 신규 생성해줘."
```

**핵심 설계 판단 (실전 경험 기반)**:

| 판단 사항 | 선택 | 이유 |
|-----------|------|------|
| `npm install` vs `npm ci` | `npm install` | package-lock.json이 없는 프로젝트에서 `npm ci` 실패 |
| `next build` vs `tsc --noEmit` | `tsc --noEmit` | 동적 라우트(`[id]`)가 있으면 `output: 'export'`와 충돌 |
| GitHub Pages vs 외부 배포 | Vercel 권장 | 동적 앱은 GitHub Pages(정적 전용) 부적합 |
| `--forceExit` | 사용 | 비동기 핸들러 미정리 시 Jest가 영구 대기하는 문제 방지 |
| `continue-on-error` | 사용 | Mock 불일치로 일부 TC Fail해도 파이프라인 전체 실패 방지 |

> **강사 노트**: CI/CD는 "한 번에 성공"하는 경우가 거의 없다. AP-Rodi-Shop에서는 7회 이터레이션을 거쳤다. 수강생에게 "실패는 정상, 디버깅이 실력"임을 강조한다. 실습 시간이 부족하면 강사가 라이브로 1회 시연하고 수강생은 과제로 완성.

**트러블슈팅**:

| 현상 | 원인 | 해결 |
|------|------|------|
| Actions가 트리거되지 않음 | yml 파일 위치/이름 오류 | `.github/workflows/` 디렉토리에 `.yml` 확장자로 저장 |
| `package-lock.json not found` | `npm ci` 사용 | `npm install`로 변경 |
| TypeScript 타입 에러 | AI 생성 코드의 타입 불일치 | `continue-on-error: true`로 파이프라인 유지 |
| Next.js prerender 실패 | `output: 'export'`와 동적 라우트 충돌 | export 설정 제거, CI에서 `tsc --noEmit`만 실행 |
| Jest 무한 대기 | 비동기 핸들러 미정리 | `--forceExit` + `timeout-minutes: 5` |

### 4.7 보충 자료: Vercel + Supabase 배포 (시연/참고)

> 이 섹션은 시연 또는 보충 자료로 활용한다. 수업 시간이 부족할 경우 슬라이드 설명으로 대체한다. P-506으로 동일 내용의 가이드를 자동 생성할 수 있다.

**배포 아키텍처**:

```
GitHub Push
    |
    v
Vercel (자동 배포)
    |-- Root Directory: src/frontend/
    |-- Framework: Next.js 14
    |
    +-- Frontend (정적 + SSR)
    |     App Router: /, /products/[id], /admin, /cart, ...
    |
    +-- API (서버리스 함수)
          Pages Router: /api/[...path]
              |
              v

              |
              v
          Supabase REST API (PostgREST)
              |
              v
          PostgreSQL Database
```

**핵심 아키텍처 결정**:

| 결정 사항 | 선택 | 이유 |
|-----------|------|------|
| API 라우팅 | Pages Router `pages/api/[...path].ts` | NextApiRequest가 Node.js HTTP 객체를 확장하여 Express와 호환 |
| DB 연결 | Supabase REST API (PostgREST) | Vercel Lambda가 IPv4 전용, Supabase DB는 IPv6 전용이므로 직접 연결 불가 |
| 모노레포 구조 | Root Directory = `src/frontend` | Frontend가 Backend를 `require()` 로 임포트 |

**실전 교훈 (배포 디버깅 6회 이터레이션)**:
- `@vercel/node` 빌더의 모듈 해석 문제 -> Next.js Pages Router API Route로 전환
- `bcrypt` 네이티브 모듈 -> `bcryptjs` 순수 JS 구현으로 교체
- Supabase DB IPv6 전용 -> REST API의 `run_query` RPC 함수로 우회
- `useSearchParams()` -> Next.js 14에서 반드시 `<Suspense>` 래핑 필요

### 4.8 보충 자료: 배포 후 검수 -- 실전 버그 사례 (시연/참고)

> "Jest 92% Pass인데 왜 회원가입이 안 되나요?" -- Mock 테스트의 한계를 체감하는 실전 사례. **P-505가 왜 필수인지를 보여주는 대표 사례**.

**사례 1: 회원가입 내부 오류 (Vercel Body Escaping)**
- 증상: 특수문자(`!`)가 포함된 비밀번호로 회원가입 시 500 에러
- 원인: Vercel이 `!` 앞에 `\` 삽입 -> JSON 파서가 `\!`를 invalid escape로 거부
- 교훈: Mock 테스트에서는 발견 불가. 라이브 환경 전용 문제는 P-505 + 디버그 엔드포인트로 진단

**사례 2: 메인 페이지 검색창 중복**
- 증상: Header + 페이지 본문에 검색창 2개 표시
- 원인: AI 코드 생성 시 여러 파일에 유사 기능 중복 생성
- 교훈: 배포 후 체크리스트에 "UI 레이아웃 육안 검수" 항목 필수 (P-505 #4)

**사례 3: 상품 이미지 깨짐 (404)**
- 증상: 상품 카드 이미지 전체 깨짐
- 원인: DB에 image_url이 등록되어 있으나 실제 이미지 파일 미존재
- 교훈: 코드 생성 시 정적 에셋(이미지, 폰트)이 누락되기 쉬움 (P-505 #3)

**테스트 자동화 vs 배포 후 검수 비교**:
