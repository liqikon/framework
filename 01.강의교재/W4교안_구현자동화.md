### 핵심 개념: 설계-코드-배포 변환 (Design-to-Code-to-Deploy)

이번 주차의 핵심은 **설계 문서에서 실행 가능한 코드, 그리고 라이브 배포까지의 자동 변환**이다. V0.41은 여기에 **병렬 실행(P-409)**과 **배포 트러블슈팅 가이드**를 추가하여 실전 운영성을 강화했다.

```
[Phase 2 산출물]                  [Phase 3 - Group B 병렬]
기능명세서 #6 ---+
API스펙 #7  ---+--> [P-409 Group B 병렬 Task]
화면설계서 #9 -+      |
서비스기획서 #3 ------+--> 인프라 #10 + DB #12 + 디자인 #13 (동시)
                          |
                          v
                  [Phase 3 - 코드 생성]
                  P-402 백엔드 (Supabase REST)
                  P-401 프론트엔드 (Next.js)
                          |
                          v
                  [Phase 3 - 배포]
                  P-406 Vercel 설정
                  P-407 토스페이먼츠
                  P-408 Supabase Storage
```

### 4.6 실습 6: P-407 토스페이먼츠 결제 연동 (20분) ★ 신규 ★

**목표**: 한국 PG사인 토스페이먼츠를 2단계 흐름(`pending → confirm → paid`)으로 연동한다. Stripe는 한국 사업자 미지원이므로 사용하지 않는다.

```
[2] POST /api/orders         -- pending 주문 생성 (DB)
       v
[3] loadTossPayments SDK     -- 토스 결제창 호출 (프론트)
       v
[4] 사용자 결제 승인         -- 토스 측 처리
       v
[5] 성공 콜백 -> /payments/success?paymentKey=...&orderId=...&amount=...
       v
[6] POST /api/payments/confirm -- 백엔드가 토스 /v1/payments/confirm 호출
       v
[7] 검증 통과 시 DB UPDATE: status='paid', payment_key=..., 장바구니 비우기
```

## 7. 강사 노트

### 7.1 수준별 대응

| 상황 | 대응 |
|------|------|
| 코딩 경험 전무 수강생 | 구현 설계 4건 + Group B 병렬 실행에 집중. 코드 생성/배포는 시연 위주, AP-Rodi-Shop 라이브 URL 분석으로 대체 |
| 프론트만 경험 수강생 | 백엔드는 "Supabase REST = SQL을 HTTP로 호출"이라는 관점 강조. orderModel.js 의 run_query/run_mutation 한 줄씩 해부 |
| 풀스택 경험 수강생 | Vercel 4대 트러블슈팅의 원인 분석에 집중: "왜 IPv6 only인가?", "왜 Body Escaping이 발생하나?" |

### 7.2 시간 조절

| 상황 | 대응 |
|------|------|
| 실습 1-2 (설계) 지연 | 실습 3-4 (코드)는 강사 시연, 수강생은 AP-Rodi-Shop 분석 |
| 실습 3 (백엔드) 초과 | 실습 5(Vercel)을 압축, 6/7(결제/Storage)는 과제 전환 |
| 전체 시간 여유 | Group B 병렬 실행 시간 측정 비교 (수강생 각자 순차 vs 병렬) |

### 7.3 Vercel 배포 트러블슈팅 빠른 참조표

| 증상 | 1차 진단 | 해결 명령/패턴 |
|------|---------|---------------|
| `JSON parse error` on POST | Body Escaping | `server.js` 최상단 커스텀 Body Parser 삽입 |
| `ECONNREFUSED 2606:...` | Supabase IPv6 | `config/db.js` → Supabase REST RPC 어댑터 |
| `Cannot find module 'bcrypt'` | 네이티브 모듈 | `npm uninstall bcrypt && npm install bcryptjs` + import 변경 |
| `ENAMETOOLONG` 빌드 실패 | 한글 경로 | `.vercelignore` 에 한글 디렉토리 명시 |
| 401 무한 루프 | ENV 누락 | Vercel 대시보드 → Settings → ENV 7종 확인 후 redeploy |
| 결제 confirm 500 | 금액 검증 실패 | DB 주문 amount와 토스 amount 일치 여부 로그 확인 |

### 7.4 주요 Q&A 예상

| 질문 | 답변 포인트 |
|------|------------|
| "왜 Group B만 병렬이고 시스템정의서는 순차인가요?" | 시스템정의서(#11)는 인프라/DB/디자인 결과를 모두 통합 참조하므로 의존성이 있다. Group B는 서로를 입력으로 받지 않으므로 병렬 가능. |
| "AI가 생성한 코드를 그냥 쓰면 되나요?" | PM은 설계 문서 기준으로 검증해야 한다. 특히 V0.41은 4대 트러블슈팅 적용 여부를 코드 리뷰 체크리스트로 둔다. |
| "Stripe는 왜 안 쓰나요?" | Stripe는 한국 사업자 미지원. 토스페이먼츠 + KRW zero-decimal 사용. 테스트키 → 라이브키 전환 시 ENV만 교체. |
| "Supabase REST가 PG 직접 연결보다 느리지 않나요?" | RTT는 늘어나지만 Vercel Lambda는 IPv4만 가능해 IPv6 only Supabase Direct에 연결 불가. REST RPC가 유일한 해법. |
| "Group B 병렬 실행이 토큰을 더 쓰지 않나요?" | 약 1.5배. 다만 컨텍스트 격리로 각 산출물 품질이 향상되며, 강사/수강생의 대기 시간이 줄어 ROI는 명확히 양수다. |
